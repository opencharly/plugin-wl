# 2026.243.0521 — docs(wl-skill): the Compositor Compatibility table gains a Hyprland column

## Summary

The `wl` skill's **Compositor Compatibility** table — the thing a reader consults to answer *"does
this method work on my compositor?"* — listed only sway / labwc / KWin, and the overview described
the verb as covering *"wlroots compositors (sway, labwc) **and KWin**"*. Meanwhile a cstream desktop
is a fully supported venue with 30+ live `wl:` checks running against it. None of that was
discoverable from the skill.

This adds a **Hyprland (cstream)** column plus a Hyprland notes section, and updates the two
overview sentences that enumerate supported compositors.

## Every cell traces to a live check, not to the protocol list

It would have been easy to fill the column from *"Hyprland implements all six wlroots protocols"*.
That is true and still not evidence that a given method works. Each cell below is backed by a named
`PASS` in a `check-cstream-pod` run on this host, and every action is paired with an **observation**
rather than an absence of error:

| claim | proving checks |
|---|---|
| `wtype` keyboard | `wl-type-command` + `wl-type-observed` (*the typed line RAN — the process exists*) |
| key combos | `wl-keycombo-interrupt` + `wl-keycombo-observed` (*the process is GONE*) |
| window focus | `wl-focus-a/-observed`, `wl-focus-b/-observed` — both directions, so A was not a coincidence |
| minimize | `wl-minimize-b-observed` (*really moved to `special:minimized`*) |
| close | `wl-close-target` + `wl-close-observed` (*named window gone, focused one survived*) |
| clipboard | `wl-clipboard-set` + a get asserting the value returns **exactly** |
| screenshot | `wl-screenshot-content` with non-uniform content |
| keymap | `hypr-keymap-set` + `hypr-keymap-observed` (*the compositor reports the new layout*) |
| routing | `wl: status` → `window=hyprctl resolution=hyprctl pointer=yes keyboard=yes clipboard=yes` |

**Four cells are deliberately not a bare YES** — grouped into three bullets below, since `wlrctl
pointer` and `xdotool` share a reason — because a table that overstates is worse than one that
omits:

- **`grim`** — YES *but* `ecosystem.enforce_permissions = true` gates screencopy **per binary**, so
  without an `hl.permission(...grim..., "screencopy", "allow")` grant every capture is denied on an
  otherwise healthy compositor.
- **`wlrctl pointer`** and **`xdotool`** — the protocol is present and the verb reports
  `pointer=yes`, but neither is exercised in-bed. They say exactly that.
- **`wlr-randr`** — routed to `hyprctl`, and carries an explicit **must not be used** on a
  GWD-driven output. The streamer owns the output size; writing it out-of-band desyncs compositor
  and encoder with **no error anywhere** (measured: both at 640x480, a `wl: resolution 1280x720`
  moved the compositor to 1280x720 while the capsfilter stayed at 640x480). This is a second-writer
  hazard, so it applies whichever tool performs the write.

## Scope: what this does NOT touch, and why

- **The published corpus copy is generated output.** `marketplace/check/skills/wl/SKILL.md` is
  produced from the refs list in `marketplace/candy/charly-marketplace/charly.yml`; editing it
  directly would be reverted by the next generate. The source of truth is the `wl-skill:` entity in
  this repo's candy manifest, which is what this PR changes. Publishing to the corpus is the
  separate, ordered follow-on: this merges and tags, then the marketplace refs bump to the new tag,
  then the corpus regenerates.
- **The other "Compositor Compatibility" headings are different tables.** `wl-overlay` tabulates
  overlay types (`Compositor | Environment | Status | Notes`), `swaync` tabulates notification-daemon
  support, and `wl-tools` describes a selkies candy that pod-hyprland deliberately does not compose.
  None is the backend-per-method table this PR extends, and I have no Hyprland measurements for
  them — so they are left alone rather than filled in by analogy.
