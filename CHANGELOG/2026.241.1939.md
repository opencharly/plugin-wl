# 2026.241.1939 — fix(wl): a nested compositor must target the socket it SERVES, not the parent's

## Summary

`envPrelude` sources `WAYLAND_DISPLAY` from the compositor's `/proc/PID/environ`. For a **nested** compositor that is the **parent's** socket — the one it connects *to* — not the one it *serves*. Every `wl:` call then targets the parent, and the failure is **silent**: a wrong target, not an error.

## Measured

Against a `gst-wayland-display` parent hosting a nested Hyprland, same host, same moment:

```
WAYLAND_DISPLAY=wayland-1  (inherited)  grim -> "compositor doesn't support the screen capture protocol"
WAYLAND_DISPLAY=wayland-2  (served)     grim -> 2,536,516 byte PNG
```

So a **healthy** stack reports a missing protocol, and any bed asserting `wl: screenshot` goes red against a compositor that is working perfectly. That is the worst shape of bug: it accuses the wrong layer.

## The fix

`hyprctl` reports the socket Hyprland actually serves, so resolve it there and export it. Two properties are load-bearing and both are tested:

- **Guarded** on a non-empty result — unguarded it would clobber a working display on a host where `hyprctl` is absent or reports nothing, breaking the case that works today.
- **Runs last**, in `EnvRecover` — earlier and the environ import overwrites it again, restoring the bug.

Non-nested behaviour is unchanged: there the served and inherited sockets are the same value.
