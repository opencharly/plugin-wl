# 2026.242.2204 — feat(wl): hypr-layers, and the wl skills move to the plugin that serves them

## Summary

Two changes that belong together: `wl:` gains **`hypr-layers`**, and the two **wl skills move
into this repo** so the method and its documentation live in the same place.

### `wl: hypr-layers`

`wl:` could not observe a single layer-shell surface. `hypr-clients`, `toplevel` and
`windows` are all toplevel-only, and on a Quickshell/wlroots desktop the bar, the
notification popups, the launcher, the OSD, the wallpaper and the lockscreen are **none of
them toplevels** — they are `zwlr_layer_shell_v1` surfaces. A bed could assert that a
terminal window opened; it could not assert that the BAR exists.

Upstream Omarchy's acceptance suite leans on this roughly 30 times, which is what surfaced
the gap.

### Why it computes a verdict instead of forwarding JSON

The other `hypr-*` methods return `hyprctl -j <query>` verbatim. For layers that is not
enough to write a check against, because a layer surface can be **mapped but parked outside
the monitor** — which is exactly how a hidden bar is implemented, since unmapping would
force the surface to be rebuilt on reveal. Shown and hidden are the same JSON except for
coordinates.

Deciding between them means comparing the surface box against the monitor's logical bounds:
scale-divided (layer boxes are logical, `hyprctl` reports monitors in physical pixels) and
axis-swapped on an odd `transform`. That is a correlation across two different hyprctl
queries — no `stdout:` matcher can express it, and pushing it into beds as a jq incantation
would put the same geometry in N places and require jq in every guest.

So the method emits one tab-separated record per surface, ending in a verdict, which turns
each assertion a bed needs into one matcher:

| assertion | matcher |
|---|---|
| present | `stdout: {contains: omarchy-bar}` |
| absent | `stdout: {not_contains: omarchy-bar}` |
| showing | `stdout: {matches: 'omarchy-bar\s.*\sonscreen'}` |
| hidden | `stdout: {matches: 'omarchy-bar\s.*\soffscreen'}` |

The plaintext-record shape follows the `mcp` verb's precedent, for the same stated reason.

### Decisions worth stating

**Intersection, not containment.** A notification sliding in from the edge, or a bar one
pixel taller than its reserved strip, is genuinely visible. The state being distinguished is
the deliberate full park (`y = -h`), and an intersection test separates those cleanly.

**`unknown`, not a guess**, for a surface on a monitor absent from `hyprctl -j monitors`. It
matches neither an `onscreen` nor an `offscreen` matcher, so a bed fails loudly instead of
reading a fabricated verdict as a real one.

**A zero or absent `scale` is treated as 1** rather than divided by — dividing would make
every bound `+Inf` and every surface trivially on-screen, which is the assertion failing
OPEN.

## The skills move

`wl-skill` and `wl-overlay-skill` documented this verb from `opencharly/layer-charly-check`,
a repo that ships none of its code. Every method added here left the skill quietly behind —
and it had, measurably: the skill documented `sway-*` and `overlay-*` and had **no mention of
the `hypr-*` family at all**. A reader following it would conclude Hyprland is unsupported.

`plugin-punktfunk` is the precedent and the shape: a sibling `*-skill:` node in the candy
manifest with `family: check, owner: <plugin>`. **`family: check` is unchanged**, so the
published path (`check/skills/wl/`) and every `/charly-check:wl` cross-reference stay valid
— family decides the path, `owner:` decides which image's OCI label carries the skill.

A new `## Hyprland-Specific Methods` section mirrors the existing sway one, plus a
subsection for `hypr-layers` covering what it is for, why it computes a verdict, the record
format, three worked assertions, and what `unknown` means.

> **Landing order matters — this is a three-repo move.** The corpus is generated from an
> authored refs list in `opencharly/marketplace`
> (`candy/charly-marketplace/charly.yml`), and **this repo is not currently in it**. So:
> (1) this PR merges and is tagged — corpus unchanged; (2) the `layer-charly-check` removal
> merges and is tagged; (3) **one** marketplace PR bumps that pin AND adds
> `@github.com/opencharly/plugin-wl/candy/plugin-wl:v<tag>`. Both in the same PR, because a
> skill `name:` is marketplace-globally-unique — adding the new ref first would put two `wl`
> skills in one generation, and removing the old first would delete them from the corpus in
> between.

## A drift hole closed while here

`TestSchemaCompilesAndCoversEveryMethod` enumerates the methods it checks **by hand**, so it
can only verify the ones somebody remembered to add. A new `case "x":` with no CUE enum entry
leaves it green, and the failure then surfaces on a live deployment as `charly box validate`
rejecting an authored step — the furthest possible place from the change that caused it.

`methods_enum_parity_test.go` derives the set from the dispatch switch by scanning
`methods.go`, and checks both directions. Both guards carry a minimum-count floor so a scan
that stops matching fails instead of passing vacuously — which it did, immediately, when the
first draft looked for the wrong function name.
